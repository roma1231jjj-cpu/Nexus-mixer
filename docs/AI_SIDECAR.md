# Nexus Voice AI — протокол sidecar

Документ описывает локальный протокол между Rust-движком Nexus-Mixer и
Python-sidecar, который выполняет RVC/DSP-конверсию голоса. Версия протокола — **1**.

> Статус: протокол, эталонный passthrough-сервер и Rust control-plane клиент
> реализованы. Realtime-аудиотракт и ONNX-инференс — следующий шаг (см. раздел 7).

---

## 1. Принципы

- **Только localhost.** Sidecar слушает `127.0.0.1`, наружу ничего не отдаётся.
  Никаких облачных запросов и телеметрии.
- **Отдельный процесс.** Падение или перезапуск модели не должен ронять
  аудиодвижок. Rust переподключается и продолжает отдавать сухой сигнал.
- **Один сокет, два типа кадров.** JSON для управления, бинарные кадры для PCM.
  Никакого HTTP-оверхеда на каждый чанк.
- **Фиксированный формат аудио.** Mono `f32le`, 48 кГц (или фактическая частота
  clock master), chunk 20–320 мс. Стерео и ресемплинг — на стороне движка.
- **Backpressure важнее качества.** Если sidecar не успевает, движок дропает
  чанк и считает `underruns`, а не блокирует realtime-поток.

---

## 2. Транспорт

```
TCP 127.0.0.1:47600        (по умолчанию, порт настраивается)
```

Один клиент — один sidecar. Соединение инициирует Nexus-Mixer. Сервер не хранит
состояние между подключениями, кроме загруженной модели.

Таймауты:

| Этап | Таймаут |
| --- | --- |
| TCP connect | 1.5 с |
| handshake (`hello` → `ready`) | 3 с |
| ping → pong | 1 с |
| чтение аудиокадра | 2 × chunk + 50 мс |

---

## 3. Кадрирование

Каждый кадр:

```
┌────────────┬──────────┬─────────────────────────────┐
│ u32 LE len │ u8 kind  │ payload (len - 1 байт)      │
└────────────┴──────────┴─────────────────────────────┘
```

`len` включает байт `kind`, но не включает сам префикс. Максимальный размер
кадра — **1 МиБ**; больше — разрыв соединения.

| kind | Значение | Payload |
| --- | --- | --- |
| `0x4A` `J` | JSON-сообщение | UTF-8 JSON |
| `0x41` `A` | Аудио | `u32 seq` + N × `f32le` |
| `0x50` `P` | Ping | пусто |
| `0x51` `Q` | Pong | пусто |

Аудио всегда mono `f32le` в диапазоне `[-1, 1]`. `seq` монотонно растёт и
возвращается сервером без изменений — по нему движок отбрасывает опоздавшие
чанки.

---

## 4. Handshake

Клиент → сервер:

```json
{
  "type": "hello",
  "protocol": 1,
  "client": "nexus-mixer/0.1",
  "sample_rate": 48000,
  "chunk_frames": 1920,
  "channels": 1
}
```

Сервер → клиент:

```json
{
  "type": "ready",
  "protocol": 1,
  "backend": "passthrough",
  "model": null,
  "sample_rate": 48000,
  "chunk_frames": 1920,
  "rtf": 1.0
}
```

Ошибка:

```json
{ "type": "error", "code": "unsupported_protocol", "message": "protocol 2 is not supported" }
```

Если `sample_rate` или `chunk_frames` не совпадают с запросом, клиент обязан
пересоздать конвертер (ресемплинг) или разорвать соединение.

---

## 5. Аудиопоток

```
клиент: [J hello] → [A seq=0 payload] → [A seq=1 payload] → ...
сервер: [J ready] → [A seq=0 payload'] → [A seq=1 payload'] → ...
```

- Сервер обрабатывает кадры строго по порядку.
- Ответ на кадр `seq` приходит до чтения следующего (для v1 допускается
  конвейер, но тогда буфер ограничен 2 кадрами).
- Passthrough-сервер возвращает samples без изменений.
- Сервер может вернуть `{"type":"drop","seq":N}` вместо аудио, если кадр
  пропущен. Клиент считает это underrun.

Ping: клиент отправляет `P` каждые 5 секунд простоя; сервер отвечает `Q`.
Отсутствие `Q` два раза подряд → `error`, переподключение.

## 6. Размеры чанков и задержка

| chunk | Кадров @48k | Задержка только sidecar |
| --- | --- | --- |
| 40 мс | 1920 | ~40 мс + inference |
| 80 мс | 3840 | ~80 мс |
| 120 мс | 5760 | ~120 мс |
| 160 мс | 7680 | ~160 мс |
| 240 мс | 11520 | ~240 мс |
| 320 мс | 15360 | ~320 мс |

Бюджет end-to-end из ROADMAP: **< 120 мс** при chunk 160 мс. Значит inference
должен укладываться в ~1.5× реального времени на выбранном GPU.

Crossfade на стыках выполняет **движок**, а не sidecar: у sidecar нет контекста
соседних чанков. Движок хранит хвост предыдущего чанка и смешивает его с началом
следующего (`crossfade_ms` из настроек AI).

## 7. Интеграция с движком

```
capture ring ──► AI tap ──► send chunk (sidecar) ──► recv processed ──► mix
                    │                                     │
                    └── dry fallback ◄── timeout/drop ◄───┘
```

Этапы:

1. **Сделано:** Rust подключается к sidecar, проверяет handshake, измеряет RTT
   через ping и показывает статус (`offline` / `loading` / `ready` / `error`),
   backend, модель и RTF в панели AI. Команды Tauri:
   `connect_ai_sidecar`, `disconnect_ai_sidecar`, `get_ai_status`,
   `ping_ai_sidecar`, `configure_ai_sidecar`. Статус также входит в
   `EngineStatus.ai`, поэтому отдельный poll не нужен.
2. **Далее:** отдельный поток `nexus-ai` держит два SPSC-кольца (dry → sidecar,
   wet ← sidecar), а master callback только читает wet и подмешивает dry/wet.
3. **RVC:** sidecar загружает `.onnx` + `.index`, делает inference и возвращает
   PCM. Модель и параметры передаются JSON-командой `configure`.
4. **Гибрид:** DSP-цепочка канала работает до отправки чанка; sidecar получает
   уже обработанный сигнал.

## 8. Эталонный сервер

`tools/ai-sidecar/sidecar.py` — stdlib-only реализация протокола:

```powershell
python tools/ai-sidecar/sidecar.py --port 47600 --backend passthrough
```

Он не содержит RVC-модели и честно возвращает `backend: "passthrough"`.
Точка расширения — класс `Converter` в файле: метод `process(samples)` должен
вернуть обработанный массив той же длины. Для ONNX достаточно обернуть
`onnxruntime.InferenceSession` в наследника `Converter` и выбрать его через
`--backend onnx --model path\to\model.onnx`.

Сервер логирует только ошибки и handshake; аудио не пишется на диск.
